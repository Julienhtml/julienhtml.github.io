Veille technologique : vibe coding et sécurité web

Le vibe coding consiste à laisser une IA écrire le code à partir de consignes en langage courant. Ma veille ne porte pas sur la pratique en général, mais sur ce qu'elle change pour la sécurité.

Problématique

Quels risques le code généré par IA introduit-il dans les applications web, et comment les sécuriser ?

Ma méthode

Je consacre environ trente minutes par semaine à cette veille, sur un créneau fixe, depuis le 16 septembre 2026.

  1. Survol, 5 minutes. J'ouvre Feedly, mon agrégateur de flux, et je repère les articles de la semaine.
  2. Lecture, 15 minutes. Je lis un ou deux articles, en priorité une source spécialisée en cybersécurité ou en développement.
  3. Notes, 10 minutes. Je rédige une fiche avec mes propres mots : le sujet, ce qu'il apporte de nouveau, le lien avec ma pratique, le concept que j'ai appris.

Les sujets que je suis en priorité

  • Slopsquatting

    L'IA invente parfois des noms de paquets qui n'existent pas. Des attaquants créent ensuite ces paquets, avec du code malveillant dedans, pour piéger les développeurs qui installent ce que l'IA leur suggère.

  • Évolution des outils SAST

    Comment l'analyse statique de code s'adapte pour repérer les erreurs typiques du code généré par les LLM.

  • Injection de prompts

    Forcer un assistant de code à produire du code malveillant à l'aide de requêtes déguisées.

Mes fiches de veille

21 septembre 2026

L'explosion des vulnérabilités liées aux agents IA

Source : blog de Snyk, article « Market shifts rapidly to agentic AI security ». Article d'analyse.

De quoi ça parle

L'article montre, chiffres à l'appui, que l'usage d'agents IA pour coder a fait bondir les nouvelles vulnérabilités de 108 % en quelques mois. Le problème principal : l'IA génère du code en masse, bien plus vite que les développeurs ne peuvent le lire et l'auditer.

Pourquoi c'est un nouveau risque

C'est un effet d'échelle. Un développeur introduit une faille de temps en temps. Un assistant IA peut en glisser des dizaines, subtiles, en quelques secondes et sur tout un projet. Comme les attaquants s'appuient eux aussi sur des machines, la revue de code manuelle ne suffit plus à combler l'écart.

Le lien avec ma pratique

Cela change ma façon de travailler. Quand je m'aide de l'IA sur mes projets, comme mon gestionnaire de tâches en Python ou mon futur site en PHP, je ne peux plus copier-coller à l'aveugle. Je passe plus de temps à relire, comprendre et tester le code généré qu'à l'écrire, pour ne pas intégrer une faille sans m'en rendre compte.

Concept appris : IA agentique. Un simple assistant suggère une ligne. Un agent IA prend des initiatives : il planifie et exécute seul des modifications complexes dans tout un projet.

16 septembre 2026

Le Top 10 OWASP pour les applications LLM

Source : OWASP. Documentation officielle.

De quoi ça parle

C'est le référentiel qui liste les dix plus grandes vulnérabilités liées aux IA génératives. Il décrit comment une IA peut être attaquée, mais aussi comment le code qu'elle produit peut compromettre une application web.

Pourquoi c'est un nouveau risque

Avant, on surveillait les failles classiques, comme les injections SQL ou le XSS. Aujourd'hui, il faut aussi se méfier du code généré lui-même : des secrets écrits en dur, ou des bibliothèques obsolètes proposées par l'IA.

Le lien avec ma pratique

En tant que développeur, cela m'oblige à ne jamais faire une confiance aveugle au vibe coding, à toujours valider les entrées et à sécuriser les chemins d'accès. Et avant tout, un œil humain compétent doit relire ce que l'IA a produit avant de valider quoi que ce soit.

Concept appris : SAST (Static Application Security Testing). Un outil qui analyse le code source sans l'exécuter pour y trouver des failles potentielles.
